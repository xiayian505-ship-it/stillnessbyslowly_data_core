24 SOLAR TERMS REFERENCE
Version: 1.0
Updated: 2026-09-06

PURPOSE
=======
This file is the source/provenance, verification policy, and implementation contract
for solar_terms_data.js and solar_terms.js.

It is intended to be readable by both humans and AI-assisted development tools.

This file is NOT executable code.

Do not infer solar terms from lunar dates.
Do not silently change timezone conventions.
Do not hide known astronomical uncertainty.
Do not claim verification work that has not been completed.

Before modifying solar_terms_data.js or solar_terms.js, read this reference first.


SUPPORTED RANGE
===============
Supported Gregorian year range:

1901 through 2100

The range is intentionally finite.

Dates outside this range are unsupported unless this reference, the dataset,
and the implementation are explicitly extended and re-verified.

Do not extrapolate beyond 1901-2100.


SCOPE
=====
Within the supported range, solar_terms.js provides access to the 24 solar terms
stored in solar_terms_data.js.

The current data model includes:

- The 24 solar terms for each Gregorian year
- Solar-term name
- Solar longitude
- UTC+8 civil date
- Lookup by Gregorian date
- Lookup of a named term in a year
- Lookup of the next solar term

The production dataset currently preserves DATE + NAME + SOLAR LONGITUDE.

It intentionally does not claim exact historical Asia/Taipei local timestamps.

Lunar-calendar conversion is NOT defined by this reference.
See lunar_reference.txt.

Festival definitions are NOT defined by this reference.


ASTRONOMICAL DEFINITION
=======================
The 24 solar terms are astronomical events defined by apparent solar longitude,
spaced at 15-degree intervals around the ecliptic.

Examples:

- Vernal Equinox / 春分: 0 degrees
- 清明: 15 degrees
- Autumnal Equinox / 秋分: 180 degrees
- Winter Solstice / 冬至: 270 degrees

Solar terms must not be derived from lunar-calendar dates.


DATA DESIGN
===========
solar_terms_data.js stores an expanded, human-readable dataset.

For each Gregorian year from 1901 through 2100, it stores 24 records containing:

- Solar-term name
- Solar longitude
- Gregorian civil date

The complete current dataset therefore contains:

200 years x 24 terms = 4,800 records

The project intentionally prioritizes:

- Readability
- Verifiability
- Maintainability

over compressed representation.

The current dataset stores civil dates rather than historical local event times
because exact historical Asia/Taipei civil timestamps have not been fully verified.

This avoids manufacturing false precision.


CANONICAL CIVIL-TIME INTERPRETATION
===================================
Intended consumer context:
Taiwan

Canonical modern comparison offset:
UTC+8

When an astronomical source publishes in Japan Standard Time (JST / UTC+9),
subtract one hour to obtain the corresponding UTC+8 clock time for comparison.

IMPORTANT:

Historical civil-time rules and daylight-saving-time histories must not be casually
substituted between Hong Kong, Japan, and Taiwan.

HKO is primarily used as an official published DATE reference across 1901-2100.

NAOJ is used as an independent astronomical calculation source.

The current production dataset stores dates only.

Any future implementation that claims exact historical Asia/Taipei civil timestamps
must explicitly verify Taiwan's historical timezone rules rather than assuming that
all historical local clock times were permanently UTC+8.

Output includes:

- Time
- Solar-term name
- Solar longitude

Published time basis:
Japan Standard Time / UT+9

NAOJ states that its long-term results are calculated using current theories and
parameters and may differ from previously published or future values.

The tool does not account for daylight-saving time.

Role:

Independent astronomical calculation and minute-level cross-check.


DATASET GENERATION
==================
The current 1901-2100 dataset was assembled as a complete 4,800-record date
candidate set.

Generation method:

- Locate astronomical roots where apparent solar longitude reaches successive
  15-degree multiples.
- Interpret resulting civil dates using UTC+8.
- Preserve name and corresponding solar longitude.
- For HKO explicitly identified midnight-boundary cases, use the HKO published
  civil date as the project's selected value.

This generated dataset is usable by the current API and test suite.

However, generated astronomical output is not treated as its own final independent
verification source.

KNOWN ASTRONOMICAL BOUNDARY CASES
=================================
WARNING:

HKO states that calculations of moon phases and solar-term times many decades into
the future may have errors of several minutes.

When an event is very close to midnight, the published civil date can consequently
differ by one day.

HKO specifically identifies solar-term date-risk cases including:

- 2051 Vernal Equinox / 春分
- 2083 Start of Spring / 立春
- 2084 Vernal Equinox / 春分

Current project values for these cases follow the HKO published civil dates:

- 2051 Vernal Equinox / 春分: 2051-03-20
- 2083 Start of Spring / 立春: 2083-02-03
- 2084 Vernal Equinox / 春分: 2084-03-19

These are known astronomical boundary cases, not ordinary software bugs.

Rules for these cases:

1. Preserve the selected authoritative published value.
2. Preserve the uncertainty warning.
3. Do not silently "correct" the date using another algorithm.
4. If authoritative sources or later revisions disagree, document the discrepancy.
5. A future AI or developer must not remove the warning merely because another
   calculation returns a different civil date.


VERIFICATION POLICY
===================
When creating or modifying solar_terms_data.js:

1. Compare HKO published solar-term dates against an independent astronomical source.
2. Convert timezones explicitly.
3. Test all 24 terms in representative years, not only equinoxes and solstices.
4. Give extra attention to events close to 00:00 local civil time.
5. Preserve source institution, URL, retrieval date, and calculation convention.
6. Record known disagreements and revisions.
7. Do not use solar_terms_data.js itself as its only test oracle.
8. Do not use a single generated astronomical algorithm as both implementation
   and sole verification source.
9. Do not claim exact historical Asia/Taipei timestamps without verifying the
   applicable historical civil-time rules.
10. Do not extrapolate beyond the supported range.


IMPLEMENTATION CONTRACT
=======================
solar_terms_data.js:

- Stores 24 solar-term records for every Gregorian year from 1901 through 2100.
- Stores date, name, and solar longitude.
- Contains 4,800 records in the current complete candidate dataset.
- Uses UTC+8 civil-date interpretation.
- Preserves selected HKO dates for documented midnight-boundary cases.
- Does not claim exact historical local timestamps.
- Must not silently extend itself beyond the documented range.

solar_terms.js:

- Depends on solar_terms_data.js.
- Provides lookup over the finite dataset.
- Rejects unsupported dates/years.
- Does not derive solar terms from lunar dates.
- Does not extrapolate beyond the supported dataset.
- Keeps solar-term logic independent from lunar-calendar conversion.

A future AI or developer modifying either file must read this reference first.
