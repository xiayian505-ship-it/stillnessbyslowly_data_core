LUNAR CALENDAR REFERENCE
Version: 0.1-draft
Prepared: 2026-09-06

PURPOSE
=======
This file is the source/provenance and implementation contract for the future lunar.js module.
It is intended to be readable by both humans and AI-assisted development tools.

This file is NOT executable code.
Do not invent, extrapolate, or silently repair lunar-calendar data that is not supported by the sources documented here.


SUPPORTED RANGE
===============
Target Gregorian range: 1901-01-01 through 2100-12-31.

The range is intentionally finite.
Dates outside this range are unsupported unless this reference is explicitly extended and re-verified.

Do not extrapolate beyond 1901-2100.
Do not guess values outside the supported range.


SCOPE
=====
The future lunar.js module may provide, within the supported range:

- Gregorian date -> Lunar date
- Lunar date -> Gregorian date
- Lunar year, month, and day
- Leap-month identification
- Lunar month length (29 or 30 days)
- Lunar-year/month boundaries

Solar terms are NOT defined by this file.
See solar_terms_reference.txt.

Taiwan festival definitions are NOT defined by this file.
They may be maintained separately.


PRIMARY SOURCE
==============
Institution:
Central Weather Administration (CWA), Taiwan

Dataset:
日曆資料－國農曆對照
Dataset ID:
A-A0087-001

Official URL:
https://opendata.cwa.gov.tw/dataset/all/A-A0087-001

Relevant published fields include:
- Gregorian date
- ROC calendar year
- Lunar year
- Lunar month
- Lunar day
- Weekday

Role:
Primary Taiwan-side official reference for Gregorian/Lunar date correspondence.


INDEPENDENT VERIFICATION SOURCE
===============================
Institution:
Hong Kong Observatory (HKO)

Dataset/Page:
公曆與農曆對照表

Official URL:
https://www.hko.gov.hk/tc/gts/time/conversion.htm

Published coverage:
1901 through 2100

Role:
Independent official cross-check of Gregorian/Lunar correspondence across the target range.

HKO also states that its official lunar-year convention uses lunar New Year's Day
(the first day of the first lunar month) as the year boundary.


2026 SOURCE QUALIFICATION TEST
==============================
Status: PASS

The 2026 official references were checked before accepting these sources for the project.

Confirmed characteristics include:
- Lunar New Year: 2026-02-17 = lunar month 1, day 1
- Lunar month boundaries agree between the official references checked
- 2026 lunar year has 354 days
- 2026 has no leap lunar month

The purpose of this test is source qualification, not proof that every date in 1901-2100
has already been individually transcribed into this file.


VERIFICATION POLICY
===================
When building the final dataset for lunar.js:

1. Use an authoritative source documented in this file.
2. Cross-check against an independent authoritative source where available.
3. Verify lunar-year boundaries.
4. Verify leap-month years and the position of each leap month.
5. Verify the first and last day around leap-month transitions.
6. Verify 29-day / 30-day lunar month lengths.
7. Verify Gregorian/Lunar conversion around Lunar New Year.
8. Record discrepancies instead of silently choosing an answer.
9. Do not use the same derived dataset as both implementation data and its only test oracle.


KNOWN LONG-RANGE / MIDNIGHT EDGE CASES
======================================
HKO warns that astronomical calculations many decades into the future can carry
several minutes of uncertainty. If a new moon occurs very close to midnight,
the resulting civil date — and therefore a lunar-month boundary — may differ by one day.

HKO specifically identifies new-moon boundary cases including:

- 2057-09-28
- 2089-09-04
- 2097-08-07

These cases MUST be explicitly checked and documented when the final 1901-2100
lunar dataset is assembled.

Do not silently "correct" an authoritative published value using an unrelated algorithm.
If authoritative sources disagree, preserve the discrepancy in this reference and
define the dataset's selected convention explicitly.


IMPLEMENTATION CONTRACT FOR FUTURE lunar.js
============================================
The future module should:

- Reject unsupported dates explicitly.
- Never extrapolate beyond the verified dataset.
- Never infer missing leap-month data.
- Never fabricate a conversion result.
- Keep calendar data separate from application-specific festival rules.
- Expose supported-range information to consumers if practical.

A future AI or developer modifying lunar.js should read this reference first.
